# Week 8 — Sprint 3: Advanced Queries & Performance

## Overview

Week 8 begins Phase 3 Sprint 3 for the **Cardiac Patient Monitoring System API**.

The week started with Sprint 3 planning and a focus on database query performance using Entity Framework Core.

Day 1 focused on defining measurable performance targets, enabling EF Core query logging, preparing realistic test data, measuring the actual SQL query count of important list endpoints, and diagnosing the N+1 query problem.

The existing list endpoints were reviewed and measured first. No N+1 problem was found in the tested production endpoints, so a dedicated diagnostic VitalSigns endpoint was introduced specifically to reproduce and measure the N+1 pattern without misrepresenting the existing implementation.

The diagnostic endpoint produced 51 SQL queries for 50 VitalSign records, establishing a clear baseline for the optimization work that will continue during Sprint 3.

### N+1 Diagnostic Scenario

Because no N+1 issue was found in the tested existing list endpoints, a dedicated diagnostic endpoint was introduced specifically for Sprint 3 performance analysis:

```http
GET /api/VitalSigns/diagnostic-n-plus-one
```

The diagnostic implementation first retrieves all VitalSign records using one database query.

It then loops through the returned VitalSigns and performs a separate Patient query for every record.

This intentionally reproduces the N+1 query pattern for measurement and optimization training.

With 50 VitalSign records:

```text
1 query  → Load all VitalSigns
50 queries → Query Patient data once for every VitalSign
```

The confirmed result was:

```text
Records: 50 VitalSigns
Actual SQL Queries: 51
N+1 Detected: Yes
Response Time: 234 ms
```

The repeated Patient SQL query was verified directly in the EF Core console logs.

This diagnostic endpoint was introduced specifically for the performance lab and does not represent a pre-existing N+1 defect in the original production endpoints.
