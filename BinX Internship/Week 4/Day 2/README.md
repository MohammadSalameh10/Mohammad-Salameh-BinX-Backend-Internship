# Week 4 — Day 2: JWT Authentication & Token Issuance

## Overview

This exercise focused on implementing JWT-based authentication for the Task Tracker API.

A login endpoint was implemented using ASP.NET Core Identity to verify user credentials. After successful authentication, the API generates and returns a signed JSON Web Token (JWT) containing the user's ID and email as claims.

JWT Bearer Authentication was configured to validate incoming tokens before allowing access to protected endpoints.

The generated token was decoded to verify its claims, and token expiration was tested by sending an expired token to a protected endpoint.

## Learning Objectives

- Explain the structure of a JSON Web Token.
- Understand what JWT claims represent.
- Verify user credentials using ASP.NET Core Identity.
- Generate and return a signed JWT after successful login.
- Configure JWT Bearer Authentication.
- Validate JWT issuer, audience, signature, and expiration.
- Understand the purpose of short-lived access tokens.
- Understand the concept and purpose of refresh tokens.
- Protect API endpoints using `[Authorize]`.
- Test JWT authentication and expiration using Postman.

## What Is a JWT?

JWT stands for:

```text
JSON Web Token
```

A JWT is a token that can carry information about an authenticated user.

After a successful login, the server issues a JWT to the client. The client can then send that token with subsequent requests instead of sending the user's email and password again.

A JWT has three parts separated by dots:

```text
Header.Payload.Signature
```

Conceptually:

```text
Header
   +
Payload
   +
Signature
   ↓
Header.Payload.Signature
```

## JWT Structure

### Header

The header contains information about the token itself, including the algorithm used to sign it.

The generated token uses:

```text
HS256
```

which represents HMAC SHA-256.

### Payload

The payload contains **claims**.

Claims are statements containing information associated with the token or authenticated user.

The JWT generated by this project contains the user's:

```text
sub
email
```

The claims represent:

```text
sub   → Identity user ID
email → Authenticated user's email
```

The token also contains information such as:

```text
exp
iss
aud
```

which represents:

```text
exp → Expiration time
iss → Issuer
aud → Audience
```

### JWT Payload Is Not Encrypted

A JWT payload can be decoded and read by anyone who has the token.

The payload is encoded, not encrypted.

Therefore, sensitive information such as passwords or secret keys should never be placed inside JWT claims.

## JWT Claims

A **claim** is a piece of information stored inside the token.

After successful authentication, the following claims are created:

```csharp
var claims = new[]
{
    new Claim(JwtRegisteredClaimNames.Sub, user.Id),
    new Claim(ClaimTypes.Email, user.Email!)
};
```

The `sub` claim identifies the Identity user, while the email claim contains the authenticated user's email address.

These claims allow the token to carry information about the authenticated user without requiring the client to resend the login credentials with every request.

## JWT Signature

The third part of the JWT is the signature.

The signature is created using the token data together with the configured signing key.

Its purpose is to allow the API to verify that the token has not been modified after it was issued.

If the contents of a signed token are changed, its signature will no longer match when the API validates it.

## Login Request

A separate request model is used for login:

```csharp
public class LoginRequest
{
    [Required]
    [EmailAddress]
    public string Email { get; set; } = string.Empty;

    [Required]
    public string Password { get; set; } = string.Empty;
}
```

The login request contains the user's email and password.

Example:

```json
{
  "email": "mohammad@gmail.com",
  "password": "Test@12345"
}
```

## Login Endpoint

The authentication controller exposes:

```http
POST /api/Auths/login
```

The controller sends the request to the authentication service:

```csharp
var token = await _authService.LoginAsync(request);
```

If authentication fails:

```csharp
if (token is null)
{
    return Unauthorized();
}
```

the API returns:

```text
401 Unauthorized
```

If authentication succeeds:

```csharp
return Ok(new { token });
```

the API returns:

```text
200 OK
```

with the generated JWT:

```json
{
  "token": "eyJhbGciOi..."
}
```

## Credential Verification

The submitted email is first used to find the Identity user:

```csharp
var user = await _userManager.FindByEmailAsync(request.Email);
```

If the user does not exist, authentication fails.

If the user exists, the submitted password is verified using:

```csharp
var result = await _signInManager.CheckPasswordSignInAsync(
    user,
    request.Password,
    false);
```

`CheckPasswordSignInAsync` checks the submitted password against the password information stored by ASP.NET Core Identity.

If the credentials are invalid, the authentication service returns `null`, which causes the endpoint to return:

```text
401 Unauthorized
```

The application does not manually compare or hash passwords during login because ASP.NET Core Identity handles password verification.

## Creating JWT Claims

After successful authentication, the user's ID and email are added to the token:

```csharp
var claims = new[]
{
    new Claim(JwtRegisteredClaimNames.Sub, user.Id),
    new Claim(ClaimTypes.Email, user.Email!)
};
```

These claims become part of the JWT payload.

## Signing Key

The JWT signing key is read from configuration:

```csharp
var key = new SymmetricSecurityKey(
    Encoding.UTF8.GetBytes(
        _configuration["Jwt:Key"]!));
```

The signing key is a secret value used when generating and validating the token signature.

The API that validates the token must use the expected signing key to verify that the token was issued correctly and has not been modified.

## HMAC SHA-256

Signing credentials are created using:

```csharp
var credentials = new SigningCredentials(
    key,
    SecurityAlgorithms.HmacSha256);
```

`HmacSha256` is the signing algorithm used by this project.

It uses the secret signing key to create the JWT signature.

## JWT Token Generation

The JWT is generated using:

```csharp
var token = new JwtSecurityToken(
    issuer: _configuration["Jwt:Issuer"],
    audience: _configuration["Jwt:Audience"],
    claims: claims,
    expires: DateTime.UtcNow.AddMinutes(15),
    signingCredentials: credentials);
```

The token is then converted to its final string representation:

```csharp
return new JwtSecurityTokenHandler().WriteToken(token);
```

The generated token contains:

```text
Issuer
Audience
Claims
Expiration
Signature
```

## Issuer and Audience

### Issuer

The **issuer** identifies who issued the token.

For this training project:

```text
TaskTrackerApi
```

is configured as the issuer.

### Audience

The **audience** identifies who the token is intended for.

For this training project:

```text
TaskTrackerApiUsers
```

is configured as the audience.

When a token is received, the API checks these values as part of token validation.

## JWT Configuration

The training project contains the following JWT configuration:

```json
"Jwt": {
  "Issuer": "TaskTrackerApi",
  "Audience": "TaskTrackerApiUsers",
  "Key": "<training-signing-key>"
}
```

The signing key used in this project is for training purposes.

The JWT signing key is a secret and should be protected similarly to other sensitive application credentials.

In a real application, secret signing keys should not be committed to source control in plaintext.

For local development, sensitive values can be placed in an appropriate local configuration that is excluded from Git, while production environments should use the hosting platform's secrets-management mechanism.

## JWT Bearer Authentication

JWT Bearer Authentication was configured in `Program.cs`:

```csharp
builder.Services.AddAuthentication(options =>
{
    options.DefaultAuthenticateScheme =
        JwtBearerDefaults.AuthenticationScheme;

    options.DefaultChallengeScheme =
        JwtBearerDefaults.AuthenticationScheme;
})
.AddJwtBearer(options =>
{
    options.TokenValidationParameters =
        new TokenValidationParameters
        {
            ValidateIssuer = true,
            ValidateAudience = true,
            ValidateLifetime = true,
            ValidateIssuerSigningKey = true,

            ValidIssuer =
                builder.Configuration["Jwt:Issuer"],

            ValidAudience =
                builder.Configuration["Jwt:Audience"],

            IssuerSigningKey =
                new SymmetricSecurityKey(
                    Encoding.UTF8.GetBytes(
                        builder.Configuration["Jwt:Key"]!))
        };
});
```

This tells ASP.NET Core how incoming JWTs should be authenticated.

## Token Validation

The configuration validates four important parts of an incoming token:

```text
ValidateIssuer
ValidateAudience
ValidateLifetime
ValidateIssuerSigningKey
```

### Issuer Validation

```csharp
ValidateIssuer = true
```

Checks that the token was issued by the expected issuer.

### Audience Validation

```csharp
ValidateAudience = true
```

Checks that the token is intended for the expected audience.

### Lifetime Validation

```csharp
ValidateLifetime = true
```

Checks whether the token is still valid and has not expired.

### Signing Key Validation

```csharp
ValidateIssuerSigningKey = true
```

Checks the token's signature using the configured signing key.

Together, these checks determine whether the incoming JWT should be accepted.

## Authentication Middleware

The request pipeline contains:

```csharp
app.UseAuthentication();
app.UseAuthorization();
```

Authentication is responsible for determining whether the incoming request contains valid authentication information.

Authorization then determines whether the authenticated user is allowed to access the requested resource.

## Protected Endpoint

The existing task endpoint was protected using:

```csharp
[Authorize]
```

The protected endpoint is:

```http
GET /api/Tasks
```

`[Authorize]` means that the endpoint requires an authenticated user.

With JWT Bearer Authentication configured, ASP.NET Core checks the Bearer token before allowing the request to reach the protected endpoint.

## Bearer Token

The client sends the JWT through the HTTP `Authorization` header:

```text
Authorization: Bearer <token>
```

After login, the client can therefore use the issued token for subsequent authenticated requests instead of sending the user's email and password again.

## Access Token Expiration

The generated access token has a lifetime of:

```text
15 minutes
```

configured using:

```csharp
expires: DateTime.UtcNow.AddMinutes(15)
```

A short-lived access token limits the amount of time that a token can be used.

This is especially important if a token is exposed or stolen because the token automatically becomes invalid after its expiration time.

## Refresh Tokens

A refresh token is a longer-lived token that can be used to obtain a new access token without requiring the user to enter their credentials again.

Conceptually:

```text
Login
  ↓
Access Token + Refresh Token
  ↓
Access Token Expires
  ↓
Refresh Token
  ↓
New Access Token
```

This allows access tokens to remain short-lived while avoiding the need for users to log in again every few minutes.

Refresh tokens were introduced as a concept in this lesson but were **not implemented in this exercise**, because their implementation was an optional stretch task.
